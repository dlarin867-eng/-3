01 Рынок и на кого равняться

Рынок разделился на два лагеря: приложения-базы данных, где пользователь ищет и подтверждает продукт вручную, и приложения-камеры, где ИИ распознаёт блюдо по фото и сам считает калории. Второй лагерь быстро выигрывает — в марте 2026 MyFitnessPal купил Cal AI именно из-за этого сдвига.

Вывод для продукта

Не пытайтесь конкурировать с MyFitnessPal шириной базы — конкурируйте скоростью ввода. Главная ценность ИИ-счётчика — сократить логирование приёма пищи с минут до секунд, даже если точность будет ниже, чем у ручного взвешивания.

02 Как ИИ распознаёт еду по фото

Есть три технических подхода, и они не взаимоисключающие — сильные продукты комбинируют их.

Классическое компьютерное зрение

Сегментация блюда на тарелке → классификация каждого сегмента (гречка, курица, соус) → оценка объёма по площади и эвристикам плотности. Быстро и дёшево в инференсе, но требует собственного датасета и плохо обобщается на «неизвестные» блюда — домашнюю еду, смешанные соусы, нестандартную посуду.

LLM с vision (Claude, GPT, Gemini)

Модель получает фото и текстовый промпт («перечисли блюда, оцени вес и калории») и возвращает структурированный ответ. Не требует своего датасета и справляется с любым блюдом, включая доменные случаи, но точность ниже, чем у специализированной модели, и есть системная ошибка.

Что показало исследование

Прямое сравнение LLM на фото еды (Claude, GPT-4o, Gemini) дало MAPE 35–38 % по калориям для Claude и GPT-4o — сопоставимо между собой — и заметно хуже у Gemini (64–110 %). Все модели систематически занижают калорийность, и ошибка растёт вместе с размером порции. Отдельная работа показала, что точный промпт («сначала опиши объём и ингредиенты, потом считай») поднимает R² оценки энергии с 0,23 до 0,60 — промпт-инжиниринг даёт больше, чем смена модели.

Оценка объёма и глубины

Самый большой источник ошибки — не распознавание блюда, а оценка порции по плоской фотографии. SnapCalorie снижает погрешность до <20 % за счёт LiDAR на iPhone и ручной проверки части фото людьми; более бюджетный вариант — просить эталонный объект в кадре (столовые приборы, монета, ладонь) как визуальный масштаб, либо давать модели инструкцию сравнивать порцию со стандартными объёмами (стакан, кулак, колода карт).

03 Базы данных нутриентов

ИИ-оценка по фото — это черновик. Финальную точность даёт сверка с базой готовых продуктов и штрихкодов, особенно для упакованной еды, где калорийность известна точно.

Рекомендация для MVP

Open Food Facts — для сканирования штрихкодов упаковки (бесплатно, без ключа, сразу в продакшн). USDA FoodData Central — как эталонный справочник сырых продуктов и готовых блюд для сверки ИИ-оценки. Nutritionix или Edamam имеет смысл подключать позже, когда нужны рестораны конкретных сетей или разбор рецептов на естественном языке — обе стоят заметных денег на масштабе.

04 Архитектура для веб-приложения

Рабочий пайплайн — это не «одна модель», а цепочка: фото → структурированная оценка → сверка с базой → подтверждение пользователем. Последний шаг критичен: раз модели систематически занижают калории, продукту нужен быстрый способ поправить оценку, а не слепо доверять первому числу.

01

Приём фото или штрихкода

Клиент (React/Next.js) делает снимок или сканирует штрихкод камерой. Штрихкод — мгновенный путь через Open Food Facts, минуя ИИ полностью.

02

Распознавание блюда через Claude vision

Фото уходит в бэкенд, оттуда — в Claude (модель с vision, например claude-opus-5 для лучшего качества или claude-sonnet-5 для баланса цена/скорость) со структурированным выводом: список блюд, вес, калории, БЖУ, доверие модели к оценке.

03

Сверка с базой нутриентов

Название блюда ищется в Open Food Facts / USDA FDC. Если найдено точное совпадение — калорийность на 100 г берётся из базы, а не из догадки модели; ИИ отвечает только за то, что не умеет база: распознавание и вес порции.

04

Подтверждение и правка пользователем

Результат показывается как черновик с ползунком порции, а не как факт. Каждая правка — сигнал: копите их для калибровки промпта и, позже, дообучения собственной модели оценки веса.

05

Журнал и дневная сводка

Подтверждённая запись уходит в дневник (Postgres): калории, БЖУ, время, фото-превью. Сводка за день/ неделю — обычная агрегация, без ИИ.

Пример структурированного вывода

Вместо парсинга свободного текста используйте output_config.format Claude API — модель обязана вернуть JSON строго по схеме, без разметки и уговоров в промпте:

{
  "type": "json_schema",
  "schema": {
    "type": "object",
    "properties": {
      "items": {
        "type": "array",
        "items": {
          "type": "object",
          "properties": {
            "name":            { "type": "string" },
            "estimated_grams": { "type": "number" },
            "calories":        { "type": "number" },
            "protein_g":       { "type": "number" },
            "fat_g":           { "type": "number" },
            "carbs_g":         { "type": "number" },
            "confidence":      { "type": "string", "enum": ["low", "medium", "high"] }
          },
          "required": ["name", "estimated_grams", "calories", "confidence"],
          "additionalProperties": false
        }
      }
    },
    "required": ["items"],
    "additionalProperties": false
  }
}

Поле confidence — не декорация: показывайте блюда с низким доверием визуально иначе (например, рамкой другого цвета), чтобы пользователь знал, где стоит поправить оценку вручную.

Стек

  • Фронтенд — Next.js/React с доступом к камере через getUserMedia, офлайн-черновик записи в IndexedDB на случай плохой сети.
  • Бэкенд — тонкий API-слой (Node или Python), который вызывает Claude, кеширует ответы Open Food Facts / USDA и пишет журнал в Postgres.
  • Модель — claude-sonnet-5 как основной выбор для баланса цены и качества vision-оценки; claude-opus-5 для сложных составных блюд или платного тарифа с более высокой точностью; claude-haiku-4-5 — для дешёвых текстовых задач вроде нормализации названия блюда перед поиском в базе.
  • Хранилище фото — объектное хранилище (S3-совместимое) с коротким сроком жизни, если приложение не хочет становиться хранилищем чувствительных данных о здоровье дольше необходимого.

05 Дорожная карта MVP

Фаза 1 — рабочий черновик 2–4 недели
  • Фото → Claude vision → структурированный JSON → редактируемая карточка блюда
  • Штрихкод → Open Food Facts (бесплатно, без ключа) как самый точный и быстрый путь для упаковки
  • Простой дневник: список записей за день, сумма калорий и БЖУ
Фаза 2 — точность 4–8 недель
  • Сверка распознанных блюд с USDA FDC / Open Food Facts вместо доверия числам от модели напрямую
  • Сбор правок пользователя как обучающего сигнала для промпта (few-shot по частым ошибочным блюдам)
  • Индикатор доверия (confidence) в интерфейсе, подсказки «сфотографируйте сверху» / «покажите масштаб»
Фаза 3 — масштаб и персонализация после product-market fit
  • Платный тариф с Nutritionix/Edamam ради ресторанных сетей и разбора рецептов
  • Оценка объёма по эталонному объекту в кадре или (на поддерживаемых устройствах) LiDAR
  • Персональные цели, интеграция с фитнес-трекерами, недельная аналитика

06 Ограничения и риски

  • Систематическое занижение калорий — все LLM в исследовании занижали энергетическую ценность, особенно на крупных порциях; закладывайте поправочный коэффициент и явно просите пользователя подтверждать большие порции.
  • Составные и домашние блюда — точность падает до 70–75 % на супах, рагу, смешанных салатах — там, где невозможно разделить блюдо на чистые сегменты по цвету и форме.
  • Это не медицинский инструмент — приложение считает калории для общего контроля, но не должно позиционироваться как средство для клинической диетотерапии без явного дисклеймера.
  • Приватность — фото еды и данные о питании — чувствительная категория; минимизируйте срок хранения фото, шифруйте журнал, продумайте GDPR/CCPA-совместимое удаление данных по запросу.
  • Доверие важнее точности — исследования показывают, что пользователи прощают неточность, если могут быстро её поправить; интерфейс правки — не второстепенная фича, а часть точности продукта.
