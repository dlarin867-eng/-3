# Сканер калорий — исследование для ИИ-счётчика калорий

*17 августа 2026 · для веб-приложения*

## Ключевые цифры

- **35–38%** — средняя ошибка (MAPE) LLM-оценки калорий по фото (Claude, GPT-4o)
- **90–95%** — заявленная точность на простых блюдах (Cal AI)
- **70–75%** — точность на домашних составных блюдах (супы, рагу, салаты)
- **<20%** — ошибка при использовании LiDAR-глубины (SnapCalorie)
- **$0** — стоимость Open Food Facts и базового тарифа USDA FoodData Central
- **~1–3¢** — ориентировочная цена одного фото-анализа через Claude API

## 1. Рынок и конкуренты

Рынок раскололся на два лагеря: приложения-базы данных (пользователь ищет и подтверждает продукт вручную) и приложения-камеры (ИИ распознаёт блюдо по фото сам). Второй лагерь быстро выигрывает — в марте 2026 MyFitnessPal купил Cal AI именно из-за этого сдвига.

| Продукт | Подход | Сильная сторона |
|---|---|---|
| **MyFitnessPal** | Поиск в базе (14 млн продуктов) + штрихкод + фото-скан | Самая широкая база, интеграции |
| **Cal AI** | Фото → распознавание ИИ, без поиска (куплен MyFitnessPal, март 2026) | Логирование за секунды, а не 10–15 минут |
| **SnapCalorie** | Фото + LiDAR-глубина + проверка человеком | Единственный с настоящим 3D-объёмом порции |
| **Foodvisor** | Фото + ручная корректировка | Сильная база под европейскую кухню |
| **PlateLens** | Фото + штрихкод + ИИ-коучинг | Персонализация под диету |
| **Cronometer** | Ручной ввод, упор на точность | Детализация по микронутриентам |

**Вывод:** не конкурируйте с MyFitnessPal шириной базы — конкурируйте скоростью ввода. Главная ценность ИИ-счётчика — сократить логирование приёма пищи с минут до секунд, даже если точность будет ниже, чем у ручного взвешивания.

## 2. Как ИИ распознаёт еду по фото

Есть три технических подхода, и они не взаимоисключающие — сильные продукты комбинируют их.

**Классическое компьютерное зрение.** Сегментация блюда на тарелке → классификация каждого сегмента → оценка объёма по площади и эвристикам плотности. Быстро и дёшево в инференсе, но требует собственного датасета и плохо обобщается на «неизвестные» блюда.

**LLM с vision (Claude, GPT, Gemini).** Модель получает фото и текстовый промпт и возвращает структурированный ответ. Не требует своего датасета и справляется с любым блюдом, но точность ниже, чем у специализированной модели, и есть системная ошибка.

> **Что показало исследование:** прямое сравнение LLM на фото еды (Claude, GPT-4o, Gemini) дало MAPE 35–38% по калориям для Claude и GPT-4o — сопоставимо между собой — и заметно хуже у Gemini (64–110%). Все модели **систематически занижают** калорийность, и ошибка растёт вместе с размером порции. Отдельная работа показала, что точный промпт («сначала опиши объём и ингредиенты, потом считай») поднимает R² оценки энергии с 0,23 до 0,60 — промпт-инжиниринг даёт больше, чем смена модели.

**Оценка объёма и глубины.** Самый большой источник ошибки — не распознавание блюда, а оценка порции по плоской фотографии. SnapCalorie снижает погрешность до <20% за счёт LiDAR на iPhone и ручной проверки части фото людьми; более бюджетный вариант — эталонный объект в кадре (столовые приборы, монета, ладонь) как визуальный масштаб, либо инструкция модели сравнивать порцию со стандартными объёмами (стакан, кулак, колода карт).

## 3. Базы данных нутриентов

ИИ-оценка по фото — это черновик. Финальную точность даёт сверка с базой готовых продуктов и штрихкодов, особенно для упакованной еды.

| Провайдер | Объём данных | Штрихкоды | Цена |
|---|---|---|---|
| **Open Food Facts** | Открытая, растущая база | Да, без API-ключа | Бесплатно |
| **USDA FoodData Central** | ~250 000 позиций | Ограниченно | Бесплатно |
| **Edamam** | 900 000+ продуктов, 2,3 млн рецептов | 680 000+ UPC | Free → $999/мес |
| **Nutritionix** | 1,9 млн+ товаров | 600 000+ UPC, сети ресторанов | от $1 850/мес |

**Рекомендация для MVP:** Open Food Facts — для сканирования штрихкодов упаковки (бесплатно, без ключа, сразу в продакшн). USDA FoodData Central — как эталонный справочник сырых продуктов и готовых блюд для сверки ИИ-оценки. Nutritionix или Edamam имеет смысл подключать позже, когда нужны рестораны конкретных сетей или разбор рецептов на естественном языке.

## 4. Архитектура для веб-приложения

Рабочий пайплайн — это не «одна модель», а цепочка: фото → структурированная оценка → сверка с базой → подтверждение пользователем. Последний шаг критичен: раз модели систематически занижают калории, продукту нужен быстрый способ поправить оценку, а не слепо доверять первому числу.

1. **Приём фото или штрихкода** — клиент (React/Next.js) делает снимок или сканирует штрихкод камерой. Штрихкод — мгновенный путь через Open Food Facts, минуя ИИ полностью.
2. **Распознавание блюда через Claude vision** — фото уходит в бэкенд, оттуда в Claude (модель с vision, например `claude-opus-5` для лучшего качества или `claude-sonnet-5` для баланса цена/скорость) со структурированным выводом: список блюд, вес, калории, БЖУ, доверие модели к оценке.
3. **Сверка с базой нутриентов** — название блюда ищется в Open Food Facts / USDA FDC. Если найдено точное совпадение — калорийность на 100 г берётся из базы, а не из догадки модели.
4. **Подтверждение и правка пользователем** — результат показывается как черновик с ползунком порции, а не как факт. Каждая правка — сигнал для калибровки промпта.
5. **Журнал и дневная сводка** — подтверждённая запись уходит в дневник (Postgres): калории, БЖУ, время, фото-превью.

### Пример структурированного вывода

Вместо парсинга свободного текста используйте `output_config.format` Claude API — модель обязана вернуть JSON строго по схеме:

```json
{
  "type": "json_schema",
  "schema": {
    "type": "object",
    "properties": {
      "items": {
        "type": "array",
        "items": {
          "type": "object",
          "properties": {
            "name":            { "type": "string" },
            "estimated_grams": { "type": "number" },
            "calories":        { "type": "number" },
            "protein_g":       { "type": "number" },
            "fat_g":           { "type": "number" },
            "carbs_g":         { "type": "number" },
            "confidence":      { "type": "string", "enum": ["low", "medium", "high"] }
          },
          "required": ["name", "estimated_grams", "calories", "confidence"],
          "additionalProperties": false
        }
      }
    },
    "required": ["items"],
    "additionalProperties": false
  }
}
```

Поле `confidence` — не декорация: показывайте блюда с низким доверием визуально иначе (например, рамкой другого цвета), чтобы пользователь знал, где стоит поправить оценку вручную.

### Стек

- **Фронтенд** — Next.js/React с доступом к камере через `getUserMedia`, офлайн-черновик записи в IndexedDB на случай плохой сети.
- **Бэкенд** — тонкий API-слой (Node или Python), который вызывает Claude, кеширует ответы Open Food Facts / USDA и пишет журнал в Postgres.
- **Модель** — `claude-sonnet-5` как основной выбор для баланса цены и качества vision-оценки; `claude-opus-5` для сложных составных блюд или платного тарифа с более высокой точностью; `claude-haiku-4-5` — для дешёвых текстовых задач вроде нормализации названия блюда перед поиском в базе.
- **Хранилище фото** — объектное хранилище (S3-совместимое) с коротким сроком жизни.

## 5. Дорожная карта MVP

**Фаза 1 — рабочий черновик (2–4 недели)**
- Фото → Claude vision → структурированный JSON → редактируемая карточка блюда
- Штрихкод → Open Food Facts как самый точный и быстрый путь для упаковки
- Простой дневник: список записей за день, сумма калорий и БЖУ

**Фаза 2 — точность (4–8 недель)**
- Сверка распознанных блюд с USDA FDC / Open Food Facts вместо доверия числам модели напрямую
- Сбор правок пользователя как обучающего сигнала для промпта
- Индикатор доверия (confidence) в интерфейсе, подсказки «сфотографируйте сверху» / «покажите масштаб»

**Фаза 3 — масштаб и персонализация (после product-market fit)**
- Платный тариф с Nutritionix/Edamam ради ресторанных сетей и разбора рецептов
- Оценка объёма по эталонному объекту в кадре или LiDAR
- Персональные цели, интеграция с фитнес-трекерами, недельная аналитика

## 6. Ограничения и риски

- **Систематическое занижение калорий** — все LLM в исследовании занижали энергетическую ценность, особенно на крупных порциях; закладывайте поправочный коэффициент и явно просите пользователя подтверждать большие порции.
- **Составные и домашние блюда** — точность падает до 70–75% на супах, рагу, смешанных салатах.
- **Это не медицинский инструмент** — приложение считает калории для общего контроля, но не должно позиционироваться как средство для клинической диетотерапии без явного дисклеймера.
- **Приватность** — фото еды и данные о питании — чувствительная категория; минимизируйте срок хранения фото, шифруйте журнал, продумайте GDPR/CCPA-совместимое удаление данных по запросу.
- **Доверие важнее точности** — пользователи прощают неточность, если могут быстро её поправить; интерфейс правки — часть точности продукта, а не второстепенная фича.
