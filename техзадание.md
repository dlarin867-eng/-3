# Техническое задание

## ИИ-счётчик калорий для тренирующихся в зале

*Версия 1.0 · 17 августа 2026*
*Основание: [[идея]], [[исследование]]*

---

## 1. Общие сведения

### 1.1 Наименование продукта
Рабочее название: **ИИ-счётчик калорий для фитнеса** (веб-приложение).

### 1.2 Назначение
Веб-приложение для учёта питания по фото и штрихкоду с автоматической подстройкой рациона (КБЖУ) под тренировочный процесс — целевой сегмент: люди, регулярно тренирующиеся в зале (набор массы, сушка, поддержание формы).

### 1.3 Цель разработки
Дать пользователю точный и быстрый способ логировать еду и автоматически получать норму КБЖУ, которая меняется в зависимости от дня тренировки, фазы цикла (масса/сушка/поддержание) и фактической динамики веса — без ручных расчётов.

### 1.4 Документы-основания
- [[идея]] — продуктовая концепция, сегмент, ключевая фича
- [[исследование]] — анализ рынка, точности ИИ-распознавания, баз нутриентов, базовой архитектуры

---

## 2. Целевая аудитория

| Параметр | Значение |
|---|---|
| Основной сегмент | Тренирующиеся в тренажёрном зале 3+ раз в неделю |
| Цели пользователей | Набор мышечной массы, сушка (снижение жира с сохранением мышц), поддержание формы |
| Уровень вовлечённости | Средний–высокий; готовы вручную вводить вес тела, тренировочные дни, корректировать записи |
| Платёжеспособность | Готовы платить за точность и персонализацию (fitness-ниша) |

**Не входит в MVP-аудиторию:** люди с медицинскими диетическими ограничениями, спортсмены с особыми клиническими потребностями (готовится под общий фитнес-сегмент, не под клиническую диетотерапию).

## 3. Термины и сокращения

| Термин | Значение |
|---|---|
| КБЖУ | Калории, белки, жиры, углеводы |
| MAPE | Mean Absolute Percentage Error — метрика ошибки оценки |
| Тренировочный день | День, отмеченный пользователем как день с силовой/кардио-тренировкой |
| Дефицит/профицит | Отрицательный/положительный баланс калорий относительно поддержания |
| Спортпит | Спортивное питание: протеин, гейнер, креатин, BCAA, предтреник и т.п. |
| MVP | Minimum Viable Product — минимально жизнеспособный продукт |

## 4. Функциональные требования

### 4.1 Профиль пользователя

**ФТ-1.1.** Система должна собирать при онбординге: пол, возраст, рост, текущий вес, цель (набор/сушка/поддержание), уровень активности, тренировочные дни недели.

**ФТ-1.2.** Система должна рассчитывать стартовую норму КБЖУ по формуле (Миффлин-Сан Жеора или аналог) на основе введённых данных.

**ФТ-1.3.** Пользователь должен иметь возможность изменить цель и тренировочные дни в любой момент из настроек профиля.

**ФТ-1.4.** Целевое значение белка должно рассчитываться в диапазоне 1,4–2,0 г/кг веса тела для набора/поддержания и 2,3–3,1 г/кг для сушки (см. [[идея]], п. 2.1), с возможностью пользователя вручную задать своё значение в разумных пределах.

### 4.2 Распознавание еды по фото

**ФТ-2.1.** Система должна принимать фото приёма пищи через камеру устройства или загрузку файла.

**ФТ-2.2.** Фото должно передаваться в Claude API (модель с поддержкой vision) со структурированным JSON-выводом: список блюд, оценка веса (г), калории, белки, жиры, углеводы, уровень доверия модели (`confidence`).

**ФТ-2.3.** Результат распознавания должен отображаться пользователю как черновик, доступный для правки (название блюда, вес порции, КБЖУ) до подтверждения записи.

**ФТ-2.4.** Блюда с низким `confidence` должны визуально выделяться (иная рамка/цвет), чтобы стимулировать пользователя проверить оценку.

**ФТ-2.5.** Название распознанного блюда должно сверяться с базой нутриентов (Open Food Facts / USDA FDC); при точном совпадении калорийность на 100 г берётся из базы, а не из оценки модели.

### 4.3 Штрихкод

**ФТ-3.1.** Система должна поддерживать сканирование штрихкода упаковки через камеру.

**ФТ-3.2.** По штрихкоду выполняется запрос к Open Food Facts; при успехе — продукт и его КБЖУ на 100 г добавляются в запись без участия ИИ-оценки.

**ФТ-3.3.** При отсутствии продукта в базе пользователю предлагается создать запись вручную с сохранением на будущее.

### 4.4 Циклирование углеводов и адаптивная дневная норма

**ФТ-4.1.** Система должна ежедневно определять, является ли текущий день тренировочным (на основе профиля пользователя или отметки в календаре тренировок).

**ФТ-4.2.** Дневная норма углеводов должна автоматически пересчитываться:
- Тренировочный день: 2,0–2,5 г/кг веса тела
- День отдыха: 0,5–1,0 г/кг веса тела, с компенсацией калорийности за счёт жиров

**ФТ-4.3.** Норма белка должна оставаться постоянной вне зависимости от типа дня.

**ФТ-4.4.** Пользователь должен видеть на главном экране текущую дневную норму КБЖУ с явным указанием типа дня («Тренировочный день» / «День отдыха»).

### 4.5 Тайминг приёма пищи

**ФТ-5.1.** Пользователь должен иметь возможность указать примерное время предстоящей тренировки.

**ФТ-5.2.** За 1–2 часа до отмеченного времени тренировки система должна показывать уведомление/подсказку, если приём пищи за этот период был низкоуглеводным.

**ФТ-5.3.** В течение 1–2 часов после тренировки система должна показывать напоминание о приёме белка с расчётом недостающего количества граммов до дневной нормы.

**ФТ-5.4.** В вечернее время (настраиваемое пользователем, по умолчанию 20:00) система должна формировать сводку с указанием недостающих граммов белка/калорий и 2–3 конкретных вариантов продуктов для добора нормы.

### 4.6 Спортивное питание

**ФТ-6.1.** Система должна предоставлять отдельную категорию ввода «Спортпит», не смешанную с общей базой продуктов питания.

**ФТ-6.2.** Быстрый ввод должен поддерживать типовые единицы измерения спортпита («мерная ложка», «капсула», «таблетка») без необходимости взвешивания.

**ФТ-6.3.** Стартовый справочник спортпита должен содержать не менее 50 популярных позиций (протеин, гейнер, креатин, BCAA, предтреник) с указанием КБЖУ на порцию.

**ФТ-6.4.** Приём креатина должен поддерживать отдельное напоминание-привычку («принять сегодня»), независимо от подсчёта калорий.

### 4.7 Дневник и автокоррекция нормы

**ФТ-7.1.** Система должна вести журнал всех записей о питании с привязкой к дате и времени.

**ФТ-7.2.** Пользователь должен иметь возможность вводить текущий вес тела вручную не реже, чем раз в 2–3 дня.

**ФТ-7.3.** Раз в 7–14 дней система должна автоматически сравнивать фактическую динамику веса с ожидаемой (согласно выбранной цели) и предлагать корректировку дневной калорийности на следующий период.

**ФТ-7.4.** Пользователь должен иметь возможность принять или отклонить предложенную корректировку нормы.

### 4.8 Отчётность

**ФТ-8.1.** Система должна предоставлять сводку за день (сумма КБЖУ, остаток до нормы) и за неделю (график калорий, среднее по белку).

**ФТ-8.2.** Система должна отображать динамику веса тела в виде графика.

## 5. Нефункциональные требования

### 5.1 Производительность
- Время ответа на запрос распознавания фото — не более 8 секунд (P95).
- Время отклика UI на действия пользователя — не более 300 мс.

### 5.2 Доступность
- Веб-приложение должно корректно отображаться на мобильных устройствах (адаптивная вёрстка, mobile-first — основной сценарий использования в зале/на кухне).
- Поддержка офлайн-черновика записи (сохранение фото и данных локально при плохом соединении, синхронизация при восстановлении сети).

### 5.3 Безопасность и приватность
- Фотографии еды и данные о питании относятся к чувствительной категории данных — минимизация срока хранения фото (по умолчанию удаление оригинала после обработки, хранение только результата распознавания, если пользователь не указал иное).
- Возможность полного удаления аккаунта и всех связанных данных по запросу пользователя (GDPR/CCPA-совместимое удаление).
- Передача данных по HTTPS, шифрование чувствительных полей в базе данных.

### 5.4 Дисклеймеры
- Приложение должно явно указывать, что не является медицинским или диетологическим инструментом.
- Значения белка выше 3,0 г/кг веса тела должны сопровождаться предупреждением и не выставляться автоматически без явного согласия пользователя.

## 6. Архитектура и технологический стек

Основано на разделе 4 [[исследование]].

| Слой | Технология |
|---|---|
| Frontend | Next.js / React, адаптивная вёрстка, доступ к камере через `getUserMedia` |
| Backend | Node.js или Python, тонкий API-слой |
| ИИ-распознавание | Claude API (`claude-sonnet-5` — основной сценарий; `claude-opus-5` — сложные составные блюда) со структурированным JSON-выводом |

| Хранилище фото | Объектное хранилище (S3-совместимое), короткий срок жизни оригиналов |
| Уведомления | Push/веб-уведомления для напоминаний по таймингу |

## 8. Пользовательские сценарии (Use Cases)

### UC-1: Логирование еды по фото
- **Предусловие:** пользователь авторизован, профиль заполнен
- **Основной сценарий:** пользователь делает фото → система возвращает распознанные блюда → пользователь подтверждает или правит → запись сохраняется в дневник
- **Альтернатива:** confidence низкий → интерфейс подсвечивает блюдо, предлагает уточнить вес вручную

### UC-2: Автоматический пересчёт нормы под тренировочный день
- **Предусловие:** у пользователя настроены тренировочные дни
- **Сценарий:** при открытии приложения в тренировочный день система показывает повышенную норму углеводов/калорий без действий пользователя

### UC-3: Быстрый ввод спортпита
- **Сценарий:** пользователь выбирает категорию «Спортпит» → выбирает продукт из справочника → указывает порции («1 мерная ложка») → запись сохраняется мгновенно

### UC-4: Еженедельная автокоррекция нормы
- **Предусловие:** накоплено ≥ 7 записей веса тела за период
- **Сценарий:** система сравнивает фактическую динамику с ожидаемой → предлагает корректировку («+150 ккал») → пользователь принимает/отклоняет

### UC-5: Напоминание о добавке белка вечером
- **Сценарий:** в заданное время система проверяет остаток нормы белка на день → если остаток > 0 → показывает сводку с вариантами продуктов

*(полный сценарий «день из жизни» — см. [[идея]], п. 3)*

## 9. Экраны приложения (MVP)

1. Онбординг: цель, параметры тела, тренировочные дни
2. Главный экран: дневная норма (с индикатором тип дня), сумма съеденного, остаток по КБЖУ
3. Экран съёмки/загрузки фото → карточка распознанных блюд (редактируемая)
4. Экран сканирования штрихкода
5. Экран «Спортпит»: быстрый выбор из справочника
6. Дневник: список записей за день/период
7. Экран веса тела: ввод + график динамики
8. Отчёты: недельная сводка по КБЖУ
9. Настройки профиля и цели

## 10. Этапы разработки

### Фаза 1 — MVP (2–4 недели)
- Фото → Claude vision → редактируемая карточка блюда (ФТ-2.*)
- Штрихкод → Open Food Facts (ФТ-3.*)
- Профиль пользователя, стартовый расчёт нормы КБЖУ (ФТ-1.*)
- Базовый дневник питания (ФТ-7.1)

**Критерий приёмки Фазы 1:** пользователь может сфотографировать/отсканировать еду, увидеть оценку КБЖУ, подтвердить запись и увидеть сумму за день.

### Фаза 2 — Спортивный слой (4–6 недель)
- Циклирование углеводов по тренировочным дням (ФТ-4.*)
- Категория «Спортпит» (ФТ-6.*)
- Тайминг приёма пищи и напоминания (ФТ-5.*)

**Критерий приёмки Фазы 2:** норма КБЖУ автоматически меняется в зависимости от типа дня; пользователь может залогировать спортпит за 2 действия; приложение присылает напоминание после тренировки.

### Фаза 3 — Точность и удержание (4–8 недель)
- Сверка распознанных блюд с базой нутриентов (ФТ-2.5)
- Автокоррекция нормы по факту веса (ФТ-7.2–7.4)
- Индикатор доверия (confidence) в интерфейсе (ФТ-2.4)

**Критерий приёмки Фазы 3:** норма калорий еженедельно предлагается к корректировке на основе фактической динамики веса; пользователь видит, каким записям стоит доверять меньше.

### Фаза 4 — Масштаб (после product-market fit)
- Платные базы нутриентов (Nutritionix/Edamam)
- Интеграция с трекерами тренировок (Strava/Google Fit/Apple Health)
- Партнёрская интеграция со спортпит-брендами

## 11. Метрики успеха

| Метрика | Целевое значение (после MVP) |
|---|---|
| Время логирования одного приёма пищи | < 15 секунд |
| Доля подтверждённых без правок ИИ-оценок | > 60% на простых блюдах |
| Удержание (retention) через 30 дней | Ориентир по fitness-нише — выше среднего по калорийным трекерам |
| Доля пользователей, ведущих вес тела регулярно | > 40% (необходимо для автокоррекции) |

## 12. Риски

| Риск | Описание | Митигация |
|---|---|---|
| Систематическое занижение калорий ИИ | LLM занижают калорийность, особенно на крупных порциях (MAPE 35–38%) | Сверка с базой нутриентов, автокоррекция нормы по факту веса |
| Заниженная точность на белке критична для сегмента | Целевая аудитория чувствительна к недобору белка на сушке | Отдельная калибровка промпта на белковые продукты, явный индикатор доверия |
| Медико-юридические риски рекомендаций | Высокие значения белка/дефицита не подходят всем | Дисклеймеры, ограничение крайних значений в UI |
| Отток пользователей при видимых ошибках | Требовательная аудитория быстро теряет доверие к неточным цифрам | Быстрый и заметный механизм ручной правки записи |
| Приватность фото и данных о питании | Чувствительная категория данных | Короткий срок хранения фото, шифрование, полное удаление по запросу |

## 13. Вне рамок MVP (Out of Scope)

- Персональные рекомендации от диетолога/тренера в реальном времени
- Клиническая диетотерапия и медицинские протоколы питания
- Интеграция с умными весами и носимыми устройствами (только Фаза 4)
- Мультиязычность интерфейса (первая версия — русский язык)
- Нативные мобильные приложения (первая версия — веб-приложение)
